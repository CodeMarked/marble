## Implementation depth (baseline vs linked runtime)

Not every header under `engine/` is backed by the same amount of **compiled** engine code.

- **Linked runtime (today):** The `engine` CMake target builds a **fixed set** of `.cpp` files (window/GLFW, Vulkan RHI, Jolt scene, core loop, input bridges, logging, and so on). That slice is what external integrators can **link** as the Marble engine library for those features.
- **Baselines and seams:** Large areas — especially under `engine/animation/`, `engine/audio/`, and much of `engine/gameplay/` — are mostly **headers** plus tests: types, math, fixed-capacity containers, and **integration contracts** aligned with book chunks and ADRs. They are **real code** for what they define, but they are **not** the same as shipping a complete audio device backend, script virtual machine, or **full production netcode**. **Exception:** `engine` links **`UdpSocket.cpp`** and **`UdpGameTransport.cpp`** with [`IGameTransport`](../../engine/gameplay/GameTransport.hpp) + session/wire headers — a **narrow** real-time path ([`ADR-0060`](../decisions/ADR-0060-multiplayer-data-plane-and-authority-constraints.md)); sequencing, interest management, and authoritative game-loop integration remain phased work ([`multiplayer-physics-world-scale.md`](multiplayer-physics-world-scale.md)).
- **Intentional defaults:** The frame loop may install a **no-op render phase** until a game injects a real one; render seams document **optional** hooks (for example clear color as no-op for headless). That is by design, not missing work in those spots.
- **Phased “fleshing out”:** Turning a baseline into a **full subsystem** (ACP packs, audio output, **deep** multiplayer stack, scripting runtime) follows **SDK phases** in [`sdk-and-samples-roadmap.md`](sdk-and-samples-roadmap.md). Phases **0–4** prioritize spine, physics/sim samples, RHI depth, a **narrow** multiplayer sample (transport + wire + `mp_foundation` today; tick-aligned authority + reliability + AOI next), and asset pipeline / profiling; **Phase 5** is where heavier gameplay, UI, and scripting depth is expected to accelerate once lower layers stabilize.

## SDK-critical path (summary)

This table ties **roadmap phases** to **what depth is in scope**, not a calendar. Work can overlap; it is ordered by **dependency**, not “finish subsystem X completely before touching Y.”

| Phase (roadmap) | Subsystem emphasis |
| --- | --- |
| **0** | Lifecycle, assets root, tests, compile and policy baselines |
| **1** | Simulation + physics vertical slice (fixed-step, middleware seam); games use **`IPhysicsScene` / Jolt** where needed |
| **2** | Render/RHI depth in parallel (passes, materials, instancing **as samples require**) |
| **3** | Multiplayer **foundation** sample: authority, tick, small replicated state — not full prediction or interest management |
| **4** | ACP, profiling checkpoints, broader platform validation |
| **5+** | Gameplay/app-shell, richer scripting, and other “thick” product features when APIs churn less |

## Boundary expectations

- Each subsystem exposes a narrow interface and explicit lifecycle hooks.
- Cross-subsystem dependencies flow through clear contracts, not ad-hoc calls.
- Data ownership is explicit to reduce coupling and simplify debugging.

## Current focus

- Landed chunk 1 baseline lifecycle contract (`init -> run -> shutdown`).
- Runtime owns frame phase ordering and shutdown ordering.
- Platform windowing remains isolated behind `platform::Window`.
- Landed chunk 2 runtime phase interfaces: simulation and rendering are dispatched through narrow contracts.
- Landed chunk 3 fixed-step simulation phase as runtime default implementation.
- Landed chunk 4 runtime assets root resolution and CMake staging of `assets/` beside `marbles`.
- Toolchain: Marble-owned targets inherit `marble_compile_options` (`/W4`, `/permissive-` on MSVC; `MARBLE_DEBUG` in Debug).
